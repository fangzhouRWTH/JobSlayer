# ADR-0004：CLI 优先的人工监督闭环

- 状态：Accepted
- 日期：2026-08-07

## 背景

JobSlayer 的核心价值包括人类对计划、风险、权限和合并的控制。若等完整 Web 平台、数据库和实时事件系统完成后才设计人工交互，领域模型很容易退化为“阅读 Agent 聊天后随意决定”。但现在直接建设复杂前端会把 Phase 0 重心从执行闭环移开。

## 决定

首先定义提供方无关的 `DecisionCard` 与 `HumanDecision`，并提供 CLI 交互：

- 卡片必须说明当前要决定什么、为什么是现在、影响范围、风险、可逆性、证据和各选项后果；
- 选项 ID、默认选项和推荐项由确定性控制器生成；
- 人工必须提供明确身份、选择和理由；
- 决策记录包含原卡片内容哈希，防止脱离所见上下文；
- CLI 只产生结构化 `HumanDecision`，不直接绕过 `WorkflowKernel` 改变任务状态；
- 自动化调用可以显式传入选择和理由，但不能伪装成已经执行状态转换。

Web 仪表板在持久任务存储、事件流和制品 URI 稳定后复用同一契约。

## 理由

- 立即获得可测试的人工门禁；
- CLI 适合本地、SSH 和 CI 环境；
- 先稳定信息模型，减少未来 UI 返工；
- 人工选择与工作流应用分离，保持代码拥有状态真相。

## 后果

- 初期没有实时图形仪表板、富 diff 或图片并排查看；
- 决策文件需要由控制器注册为制品并应用到合法状态转换；
- CLI 输出必须避免泄露证据中的秘密，后续需要制品访问控制和脱敏。

## 替代方案

- 立即开发完整 Web UI：暂缓，持久 API 和事件模型尚未稳定。
- 直接询问“是否批准”：拒绝，缺少证据、风险和后果上下文。
- 让 Agent 根据自然语言回复自行判断审批：拒绝，状态与授权不可审计。

## 退出策略

CLI 和未来 Web UI 都消费相同 `DecisionCard` 并产生相同 `HumanDecision`。前端替换不会迁移工作流或审批领域数据。
