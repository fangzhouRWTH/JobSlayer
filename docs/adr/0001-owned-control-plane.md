# ADR-0001：拥有控制平面与领域模型

- 状态：Accepted
- 日期：2026-08-06

## 背景

JobSlayer 面向包含大型 C++/Python 代码、GPU 构建、图形与仿真资产、长时间训练和昂贵验证的工程项目。Agent 框架和模型提供方迭代很快，且其对话、图或角色对象无法天然表达本项目的审批、证据、风险和硬件血缘。

## 决定

项目自行拥有领域契约、确定性工作流、权限/风险政策、上下文包、制品血缘、验证门禁和人工控制界面。编码 Agent、模型 SDK、容器、CI、观测和分布式计算系统均通过窄适配器接入。

工作流状态只能由代码转换。模型可以建议状态变化，但不能直接完成任务、改变验收标准或扩大权限。

Phase 0 使用 Python、Pydantic 契约和本地追加日志。只有出现已验证的恢复与协调需求后才引入 PostgreSQL/Temporal；只有出现集群计算需求后才引入 Ray/Kubernetes 工作流。

## 理由

- 供应商和运行时可替换；
- 工程完成条件可确定、可测试；
- 权限与高风险动作不依赖提示词；
- 同一任务能公平比较不同执行器；
- 失败、修复和审批保留为不可覆盖的历史。

## 后果

项目需要维护自己的契约、状态机、迁移和适配器测试，但避免了把长期业务语义绑定到短期框架。外部框架的新功能只有在内部接口无法表达真实需求时才推动接口演进。

## 替代方案

- 直接以某个 Agent 框架的 graph/team/agent 对象作为产品模型：拒绝，迁移和治理风险过高。
- 以自由对话和 Agent 共识决定流程：拒绝，无法可靠审计和验证。
- Phase 0 立即采用 Temporal/Kubernetes：暂缓，当前没有足够的长任务和集群证据来抵消运维成本。

## 退出策略

任一外部适配器必须能够在不迁移核心任务、证据和状态数据的前提下移除。若 Python 控制平面未来不能满足性能或部署要求，领域契约以版本化 JSON Schema 作为迁移边界。
